# Identifier Selection — UID and Primary Key

Separating the **logical identifier (UID)** from the **physical primary key**, and choosing each
against the storage model of the target engine. The compact decision table is in `../SKILL.md`
Stage 3; the reasoning is here.

## Universal Rules

- A PK must be `NOT NULL`, `UNIQUE`, and **immutable**.
- Prefer a single, short column.
- Business identifiers that can change or be exposed — national ID, email, business registration
  number — belong in a `UNIQUE` constraint, **not** the PK.
- If creation time is needed, add a `created_at` column. Do not encode it in the key.
- **Never use a raw timestamp alone as a PK.** Concurrent creation collides, and clocks run
  backwards (NTP correction, leap handling, VM migration).
- Store UUIDs as native `uuid` or 16-byte binary, never as a 36-character string. RFC 9562
  recommends the 128-bit binary representation for database storage.
- A UUID is an identifier, not a secret. **Never treat possession of a UUID as authentication or
  authorization** — unguessability is not an access control.

## Identifier Types

| Type | Strength | Watch out for |
|---|---|---|
| Sequential integer | Small, fast, high ordering locality | Needs central generation or allocated ranges |
| UUIDv4 | Distributed generation, unpredictable | Random insert position, poor index locality |
| UUIDv7 | Distributed generation **and** time-ordered | Generator quality and clock handling matter |
| Natural key | Business meaning is explicit | Changes, length, PII exposure |
| Composite key | Expresses business uniqueness directly | Inflates every secondary index and referencing column |

UUIDv4's generation order is unrelated to its sort order, so B-tree insert positions scatter.
UUIDv7 carries a Unix timestamp in its leading bits, which restores time ordering and index
locality (RFC 9562).

## MySQL / InnoDB

InnoDB uses the PK as a **clustering index**: row data lives in PK order in the B-tree leaves.
Every **secondary index record also stores the PK value**, so a wide PK inflates every index in
the table.

Both facts make PK width and PK ordering a storage decision, not just a modeling one.

Policy:

1. Default to `bigint unsigned AUTO_INCREMENT` for ordinary tables generated by a single database.
2. If distributed generation is required, use **UUIDv7** or a time-sortable 64-bit ID.
3. A random **UUIDv4 as the clustering PK is permitted only against a stated requirement** —
   it fragments the clustering index and inflates every secondary index.
4. Store UUIDs as `binary(16)`, never `char(36)`.
5. Wide natural keys and composite keys go in a `UNIQUE` constraint, not the PK.
6. When an externally visible ID is needed, separate the internal PK from the public UID.

```sql
CREATE TABLE purchase_order (
  id         bigint unsigned NOT NULL AUTO_INCREMENT,
  public_id  binary(16) NOT NULL COMMENT 'UUIDv7, app-generated; external-facing UID',
  created_at timestamp(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  CONSTRAINT pk_purchase_order PRIMARY KEY (id),
  CONSTRAINT uq_purchase_order_public_id UNIQUE (public_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### The `UUID_TO_BIN` Swap Flag Applies to v1 Only

`UUID_TO_BIN(uuid, 1)` rearranges the time fields of a **UUIDv1** so the binary form becomes
time-ordered. MySQL's own `UUID()` produces v1, which is why the flag exists.

**Do not apply the swap flag to a UUIDv7.** v7 is already time-ordered in its natural byte order;
swapping its fields destroys that ordering — the exact property you chose v7 for.

```sql
-- v1 from MySQL UUID(): swap makes it time-ordered
SELECT UUID_TO_BIN(UUID(), 1);

-- v7 generated in the application: NO swap flag
SELECT UUID_TO_BIN('01912d4e-8f3a-7c21-9b7e-2f5a6c1d4e30', 0);  -- or simply UUID_TO_BIN(v)
```

Be consistent per column, and record which convention a column uses in its `COMMENT` — reading a
v1-swapped value as unswapped (or vice versa) silently produces wrong UUIDs.

## PostgreSQL

PostgreSQL stores rows in a **heap**. A PK creates a unique B-tree index but does **not** keep the
table physically ordered by it. `CLUSTER` reorders once; rows written afterwards are not
maintained in that order.

So PK choice is driven by logical stability, immutability, uniqueness, and join convenience rather
than by clustering. **Random UUID cost is reduced, not eliminated** — index locality still affects
the PK's own B-tree, so write-heavy tables still prefer ordered keys.

Policy:

- Single-system tables: `bigint GENERATED ALWAYS AS IDENTITY`.
- Distributed generation: native `uuid` type with **UUIDv7**.
- Write-heavy tables: UUIDv7 over UUIDv4, for the same index-locality reason.
- Natural keys stay out of the PK when they can change.
- **`uuidv7()` is built in from PostgreSQL 18.** On 16 and 17 (this plugin's baseline is 16.7+),
  generate v7 in the application or use a vetted extension. `gen_random_uuid()` is v4 — do not
  reach for it when you wanted ordering.

```sql
-- PostgreSQL 18+
CREATE TABLE app.purchase_order (
  purchase_order_id   uuid PRIMARY KEY DEFAULT uuidv7(),
  created_at timestamptz NOT NULL DEFAULT current_timestamp
);

-- PostgreSQL 16 / 17: v7 supplied by the application
CREATE TABLE app.purchase_order (
  purchase_order_id   uuid NOT NULL,   -- UUIDv7 generated in the application
  created_at timestamptz NOT NULL DEFAULT current_timestamp,
  CONSTRAINT pk_purchase_order PRIMARY KEY (purchase_order_id)
);
```

## Selection Table

| Condition | MySQL / InnoDB | PostgreSQL |
|---|---|---|
| Single DB, ordinary business table | `AUTO_INCREMENT` | `IDENTITY`, or UUIDv7 |
| Write-heavy | Sequential integer first | `IDENTITY` or UUIDv7 |
| ID generated on multiple nodes | UUIDv7, or a distributed integer ID | UUIDv7 |
| ID exposed externally | Internal integer PK + public UID | UUID PK, or a separate public UID |
| Strong unpredictability required | Internal PK + UUIDv4 public ID | UUIDv4, or a separate public ID |
| Wide natural key | Split out as `UNIQUE` | Split out as `UNIQUE` |

## Warn On These

Flag each of these in a design or review:

- An InnoDB table with no explicit PK
- An InnoDB PK that is a UUIDv4 or a long string
- An InnoDB PK that is a needlessly wide composite key
- A UUID stored as `char(36)`
- Mutable business data used as the PK
- A raw timestamp used as the sole PK
- A UUID used as an authentication or authorization mechanism
- A random-UUID PK on a write-heavy PostgreSQL table with no stated reason
- `UUID_TO_BIN(v, 1)` applied to a UUIDv7

## Final Policy

> On MySQL InnoDB, default to a short sequential PK — `AUTO_INCREMENT` for the ordinary
> single-database case. Use a time-sortable identifier such as UUIDv7 when distributed generation
> is required. On PostgreSQL the logical criteria can lead, but write-heavy tables should still use
> `IDENTITY` or UUIDv7 for index locality. Separate business identifiers and externally visible
> identifiers from the physical PK when the situation calls for it.
